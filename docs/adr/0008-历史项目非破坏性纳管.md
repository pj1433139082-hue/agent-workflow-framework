# ADR 0008：历史项目非破坏性纳管

## 背景

在实际工程落地中，使用者不仅需要从零创建全新的业务项目，还大量存在将既有历史项目（包含已有的业务代码、Git 版本历史、构建脚本与依赖定义）引入通用智能体协作框架的改造需求。
既有的 `agent_workflow start` 命令为防止数据覆盖，设计了强硬的 `workspace_exists` 阻断机制；若使用破坏性覆写或手工拼凑文件，极易损坏老项目的核心代码、污染版本提交历史或覆盖关键环境配置。

## 决定

1. **原生提供非破坏性纳管指令 (`adopt`)**：
   - 框架核心 CLI 提供公开命令：`python -m agent_workflow adopt <已存在项目目录> --project-id <ID> [--apply]`；
   - 明确语义边界：`start` 仅用于尚不存在的新目录；`adopt` 专用于纳管已存在的合法工作区目录。
2. **渐进式非破坏性并入 (Non-destructive Ingest)**：
   - **源码与 Git 历史绝不动**：老项目原有的代码目录、测试、`.git`、版本提交记录逐字节保留，绝不移动或改名；
   - **既有文档与配置冲突保护**：
     - 若老项目已有 `README.md`，则列入保留项（`preserved_files`），不作覆盖；
     - 若老项目已有 `AGENTS.md`，保留原有业务配置，生成 `AGENTS.framework.md` 供人工对比合并，避免抹除已有代理或网络代理设定；
     - 若已存在 `.gitignore`，安全追加框架本地运行时配置规则，不覆写既有忽略规则；
   - **协作骨架安全补齐**：安全注入 `docs/` 四层规范目录（入口层、流程层、规则层、触发层）、`project.json`、`tasks/kickoff` 基础任务记录及 `.agent-workflow.local.json` 框架指引。
3. **既有环境自适应探测**：
   - `adopt` 执行时自动嗅探工作区中已有的运行时与依赖配置文件（如 `requirements.txt`、`pyproject.toml`、`package.json`、`Cargo.toml`、`go.mod` 等）；
   - 将嗅探到的环境信息自动记录在首任务 `plan.md` 或 `environment.md` 中，作为业务环境的初始事实，严禁强制重新安装或修改宿主全局环境。
4. **首任务聚焦现状梳理与无缝接管**：
   - 默认创建 `kickoff`（历史项目现状与改造梳理）任务，将老项目的边界梳理作为首阶段门禁；
   - 梳理完成后直接接续业务改造，无需重复交办。

## 取舍

`adopt` 放弃了“整仓强制统一格式化”的一刀切做法，采用“安全保留 + 补齐缺失 + 生成比对模板”的增量策略。虽然保留老项目异构文件可能需要人工作一次最终审查，但彻底杜绝了数据丢失与 Git 历史损坏的灾难性风险。

## 后果

- 历史存量项目能够平滑、零风险接入通用智能体协作底座；
- 智能体能够立即通过老项目的 `AGENTS.md` 和首任务索引安全接管老项目。
