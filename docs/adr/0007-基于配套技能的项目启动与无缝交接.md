# ADR 0007：基于配套技能的项目启动与无缝交接

## 背景

当使用者希望基于通用协作底座开启一个全新的业务项目时，如果手动复制框架仓库或在框架内部直接新建目录，会导致通用底座与特定业务资产互相污染；若重新拼装一套 ad-hoc 状态机，又会丢失标准化任务定位、分流与交接能力。

## 决定

1. **配套专用启动技能 (`project-start`)**：
   - 框架在 `.skillshare/skills/project-start/` 维护项目启动配套技能，并同步至宿主环境；
   - 技能内置专用定位与转发脚本 `scripts/start_project.py`，支持基于环境变量、显式参数、当前工作区定位与源码 checkout 的安全发现，严禁硬编码绝对盘符或自动联网拉取未知包。
2. **框架外外部独立工作区隔离**：
   - 新项目工作区严格建立在框架仓库之外，且必须是尚不存在的新路径；
   - 严禁将“创建新项目”理解为覆盖已有目录或直接修改框架分发源；
   - 启动脚手架仅生成轻量项目入口（`AGENTS.md`、`README.md`、`CONTEXT.md`、分层文档骨架及 `.agent-workflow.local.json` 本地指引），不预置 Git 远端、不执行外部平台部署。
3. **按需补全与零污染原则**：
   - 默认轻量化启动，不强制预置全部辅助卡；
   - 架构、运行环境、进度、结果等辅助文档通过 `project-docs` 按需补建，不重新运行 `start`，不覆盖已有业务事实。
4. **范围与档位无缝交接**：
   - 用户原始指令中若仅包含“帮我启动项目”，则状态机止于规划阶段（`ready`）；
   - 若原始指令已明确包含后续实现或特定部署，规划完成后直接沿用原执行档位无缝交接，严禁打断用户并要求“请您针对同一目标重新交办一次”。

## 取舍

启动技能必须依赖框架提供的公开 CLI（`start` 与 `project-docs`）并遵守严格的参数传递接口，禁止直接读写内部 Python 模块；代价是启动阶段需要经过标准脚手架渲染，但彻底保障了框架与业务项目之间的物理与逻辑隔离。

## 后果

- 新项目拥有清晰纯净的独立空间，随时可作为独立 Git 仓库维护；
- 智能体能够在新项目中实现从启动到实现的无缝过渡。
