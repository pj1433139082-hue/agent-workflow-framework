# ADR 0006：交互档位作为执行节奏约定

## 背景

在人机协同或自主智能体推进任务时，不同场景对交互停点的需求不同：有时需要快速流转已确认步骤，有时需要在关键写入前人工审阅。若将这种停点偏好实现为文件系统或 CLI 权限沙箱，会导致权限模型复杂化，甚至让智能体产生“在全自动档下拥有任意删除或外部发布特权”的误解。

## 决定

1. **三档执行节奏设计**：
   - `assisted`（推荐默认）：自动完成可证明的事实调查与已交办本地步骤；同一时点独立业务决定集中一轮展示并附带推荐；用户回复后继续，不逐命令追问。
   - `full-auto`：连续处理已交办的本地推进，遇到未决必填业务决定（`ASK` / `CONFIRM`）立即安全停下并集中询问，禁止自行猜测业务答案。
   - `manual-review`：只读调查自动执行；在任何实质性本地写入、任务方案修改或状态跃迁前展示变更计划并暂停等待人工确认。
2. **档位不等于安全权限沙箱**：
   - 交互档位仅控制何时汇报与等待；
   - 所有档位的本地写入均由显式 `--apply` 触发，具备完全同等的代码审计踪迹；
   - 所有档位必须通过完全相同的业务包硬规则门禁，全自动档不能绕过任何校验或检查。
3. **单次选择与精准回答**：
   - 任务首次创建时选择一次档位并持久化记录，后续续接自动恢复原档位；
   - 针对集中展示的推荐，用户回复“全部按推荐”仅关闭本轮已展示的决定项，严禁对依赖未来证据的未决项作推定确认。

## 取舍

牺牲了基于档位的细粒度命令级 ACL 隔离，换取了极其清晰直观的心智模型：档位只管“节奏与停点”，安全与事实交由“显式命令契约与不可变门禁”负责。

## 后果

- 协作流转顺畅，避免无休止的“是否允许执行只读命令”干扰；
- 杜绝智能体基于自动化档位擅自扩大业务授权的风险。
