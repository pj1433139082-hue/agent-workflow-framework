# ADR 0009：智能体提问纪律与批处理问答

## 背景

智能体在执行任务时，若缺乏严格的交互约束，极易产生“喋喋不休、碎步打扰、反复求证”的负面体验：智能体经常向使用者询问完全可以从代码、配置、Git 或测试证据中自行推导的事实；或者在多个回合中零散提问；或者在断点恢复后重复询问已经获答的决定。这种低效交互不仅浪费上下文与 token，更极大打断使用者的心流。

## 决定

1. **确立智能体提问六大铁律**：
   - **可算不问**：凡是能从项目代码、测试结果、Git 历史、依赖清单或环境中自动计算出的事实，严禁向使用者发问；
   - **批量集中**：若当前阶段存在多个缺失的业务决定，必须合并为单轮集中提问，按编号逐项陈述**背景、业务影响、推荐选项与其他备选项**；
   - **一键确认**：支持使用者用“全部按推荐”单次回执批准整轮所有推荐项，智能体必须将其映射为各具体选项的值持久化，禁止直接记录无语义的“按推荐”字样；
   - **可见消息保底**：提问必须首先在可见对话文本中完整输出选项，再尝试调用客户端结构化选择组件，确保在客户端组件未渲染或未捕获时交互不中断；
   - **问过即锁**：用户回答后，立即通过 `agent_workflow decision` 写入任务记录，并绑定当前证据文件的 SHA256 哈希；证据未变更前，后续步骤与断点恢复严禁重复索要同一答案；
   - **只读零打扰**：只读检查、状态诊断、代码阅读与进度汇报任务，严禁弹出档位选择或业务审批。
2. **档位与问答正交**：
   - 交互档位（`full-auto`、`assisted`、`manual-review`）仅在首次可写任务启动时确认一次；
   - 档位仅约定暂停节奏，绝不能将档位或一次问答确认解释为永久外部操作许可。

## 取舍

智能体在发问前必须付出一定的推理和证据分析成本，先行查明上下文与代码事实；只有真正不可推导的业务取舍才交由使用者决定。这增加了智能体的初始分析负载，但大幅削减了不必要的会话往返。

## 后果

- 彻底根除智能体“碎步提问”与“重复求证”的痛点；
- 人机协作效率与决策可追溯性得到本质提升。
