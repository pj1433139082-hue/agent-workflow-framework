# 项目模板复用与接入对齐验收

日期：2026-10-04。本记录覆盖按需项目文档及 project-start 接续规则的本地变更；不代表提交、推送、发布或真实业务项目交付。

本页是历史验收，不是当前操作指引。当时的手工补模板已由公开 project-docs 替代；当前使用见[一键启动新项目](../00-入口层/03-一键启动新项目.md)与[已有项目文档补建验收](37-已有项目文档补建验收.md)，联合续接见[冷启动与恢复验收](38-冷启动与恢复联合验收.md)。

## 采用方式

吸收既有项目卡的职责，不复制整套模板：目标与范围只在任务 payload.json，计划与选型只在 plan.md；环境、架构、进展、总结和结果口径按实际需要生成。研究专属实验台账由相应业务包另行定义，不作为通用启动条件。

`start` 默认仍生成 14 个文件。可重复的 `--with-docs` 只接受 environment、architecture、progress、summary、results；所选文档位于 docs/project/，重复选项去重。创建后使用模板正常编辑是本次历史版本的做法，现已替换为 project-docs；不重复 start，已有工作区不会被 start 覆盖。

空总结为 draft，没有完成日期。进展是事件记录而非第二个状态源；ready 只表示启动规划有效。结果模板不预填实验值，也不把某个最佳指标指定为通用正式结果。

## 边界和下一步

本轮没有迁移真实项目、修改旧模板、初始化业务 Git 仓库、上传真实资产、操作外部业务系统或推送 GitHub。新变更尚未执行 Linux CI；能读取和调用安装副本，不等于客户端已重新发现技能或 hook 已实际触发。

辅助文档不自动进入 kickoff 的机检契约，也不能单凭文件存在证明环境可运行或业务交付完成。正式交付的证据及评价口径须由实际业务包定义；长期进展和总结只在有真实事件或证据时填写。

冷启动反馈已处理：规则明确先记录已提供的事实，只问剩余业务缺项；指南说明 project_files 是入口/辅助模板清单，不包含另行生成的 project.json 和任务记录。保留原 CLI 字段契约，不因此新增状态源或确认轮。

后续新项目由 project-start 集中处理已知目标与剩余缺项，沿用所选档位；普通项目总结存入自身目录，不把项目工作日志当作框架治理日志。
