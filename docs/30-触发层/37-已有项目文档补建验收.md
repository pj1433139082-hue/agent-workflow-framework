# 已有项目文档补建验收

## 范围与公开入口

对应 [#5：为已有项目安全补建五类辅助文档](https://github.com/pj1433139082-hue/agent-workflow-framework/issues/5)，审查基点为用户确认的 #4 提交 ed065080e8629e5d9aa427812a9c41762904571d。默认 14 文件骨架、project_files 字段含义、schema、业务包、任务事实和证据范围不变。本票不自动接入历史项目或完成业务系统。

从框架源码目录调用：

```text
python -m agent_workflow project-docs <已有项目绝对路径> --task-id <实际ID> --with-docs environment --with-docs progress
```

默认预览零写入；加 --apply 只补缺失项。可选 environment、architecture、progress、summary、results，重复选择去重。任务必须真实有效，缺失/无效身份、空/未知选择、链接、Windows junction/reparse、目录和其他类型冲突拒绝。不为每张文档增加确认轮，沿用该任务原档位和交办范围。

## 发布与恢复边界

初次 start 与后续 project-docs 共享模板选择/渲染规则，使用实际任务 ID；项目名称与目标仍只保留在任务资料事实中。总结为 draft、无完成日期；结果与表格没有预填业务结果。补建不写项目/任务事实、决定、阶段、档位、业务包绑定或索引，也不把根目录辅助文档纳入任务证据。

先核验所有可预见落点与所选模板，再逐文件发布。同目录暂存完整文件，通过独占硬链接创建目标；不覆盖已有普通文件，不支持硬链接的文件系统会失败，不降级为覆盖。预览后出现的同名普通文件也保留。路径核对并非对抗恶意目录替换的原子隔离，不宣称多文档事务。

成功与应用失败均通过顶层 progress 报告 created、preserved、pending 文档标识列表；执行失败仍为 ok=false、结构化 error 和退出码 2，不回显正文或凭据。保留既有文件和已创建项，查明冲突后再次 project-docs 仅补缺失。暂存未知或无法清理时保留待检查，不递归或通配删除。

这与事实已提交、索引未完成时的 completion 恢复不同：补文档不重放 start、不触发事实变更，也不为补文档刷新索引；事实写入失败后的恢复继续按 completion 同目标 context --write。

## 公开行为验收

tests/test_project_document_completion.py 仅走公开 CLI/技能脚本和真实临时文件系统。首个 project-docs 测试先在缺少入口时失败，再实现。后续逐项覆盖五种文档单独与混合选择、去重、默认预览、重复保留、相同渲染、自定义任务 ID、空表格及事实/索引不变。

CPython 文件审计协调器只在测试子进程的 OS 发布事件处通知父进程，制造真实同名文件、类型冲突与 I/O 故障；不 patch 私有函数、不增加生产注入开关、不断言内部调用顺序。测试保留并发普通文件、拒绝发布时出现的链接；中途失败保留 architecture，排除测试障碍后只补 environment/summary，任务字节和索引仍匹配。

Windows 路径用真实 junction/reparse 演示，Linux 用符号链接；模板使用隔离副本，验证应用重新读取预览之后的模板更新，以及非法占位、超限、非法编码、目录占位的应用前拒绝。另验证已有有效回答不因补文档失效，未通过正文条件的阶段仍不能推进。
