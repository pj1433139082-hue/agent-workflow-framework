# 冷启动与恢复联合验收

## 范围与版本

对应 [#6：无上下文启动、续接、补文档与恢复联合验收](https://github.com/pj1433139082-hue/agent-workflow-framework/issues/6)，基点为 #5 提交 961ef4b501d6a18a3e4def5064b5e7567c828c3c。#4 的事实写入和 #5 的文档补建均先独立验收，本票只联合公开使用体验，不挪用尚未实现的错误分支、不增加核心状态机或业务门禁。

保留 schema 1.0、创建时完整业务包绑定、事实与索引分离、仓库外项目和不覆盖边界。仅本地合成规划，不修改真实模型、权限、代理、VPN 或全局技能；不推送、合并、关闭远端票据或写真实业务系统。

## 同一项目的可复现回归

从克隆仓库根目录运行：

```text
python -m unittest tests.test_cold_start_acceptance -v
```

tests/test_cold_start_acceptance.py 创建仓库外临时项目，显式使用非默认任务 launch-not-kickoff 和 assisted；公开 start 先预览零写，再创建默认 14 文件，不生成辅助空卡。所有业务字段/回答都来自测试定义的合成使用者，不是模板推断的真实事实。

同一个项目依次核验：

| 联合场景 | 所需结果 |
| --- | --- |
| 范围缺失、尚未通过的方案正文 | advance 拒绝；有效当前合成回答可记录，不能因此绕过正文检查 |
| 回答事实提交后，索引发布被真实目录阻挡 | operation=completed、local_record=incomplete、repeat_operation=false；动作已完成，不能把它改报为整个未执行 |
| 按 completion 修复索引 | 同目标 context --write；task.json 字节不变，不重放 decision 或 advance |
| 既有 progress 内容，中途补建 environment 被阻挡 | 顶层 progress 保留 architecture 与原 progress，environment/summary 待补；不冒充事实 completion |
| 排除测试障碍后补文档 | 同一 project-docs 只补缺失，原文件、全部事实与索引字节不变 |
| 索引漂移和非法 JSON | status/context 只读发现，显式 context --write 修复，不以索引覆盖事实 |
| 档位续接与真实验收回答 | assisted/full-auto/manual-review 均在独立命令续接中保持；修改方案使旧回答失效，只有重新提供的合成回答才接受 |
| 终态及 hook 后备 | ready/completed_locally 只表示本地规划，business_system_state 仍 not_queried；空 summary 仍 draft，hook 无唯一目标不猜任务、不写文件 |

测试只走公开 CLI/只读 hook 和真实临时文件系统，测试侧审计通知用于在 OS 事件处制造冲突，不 patch 私有函数或新增生产注入开关。结束后回收自己拥有的临时夹具，不处置未知项目。档位机检/持久化不是“智能体实际暂停”的 UI 证明；实际提问体验另见下节。

## 无对话上下文的独立执行

使用 gpt-6-luna/max、fork_turns=none 从独立临时 Git 克隆进入，只给环境、合成用户原话和允许的测试根目录，不给旧对话、拟定答案或缺陷结论。框架副本只读，生成项目在副本之外，使用者没有指定的真实业务内容不补猜。合成提问通过主智能体充当测试使用者作答，不向真实用户弹演示问题。

独立执行者从框架 AGENTS.md → 协作总览 → workflow-router → project-start → 新项目入口进入；创建后从项目自己的 AGENTS.md → 项目总览 → context/status → 当前阶段所需的规则与 SOP 续接。按需补文档时才读 project-documents 引用，不预载全部层。

合成使用者给出虚构商品资料清单项目、目标、使用者、范围、排除项、验收标准和 assisted，但未选项目子目录。执行者的实际问题只有：

| 实际待定项 | 推荐与备选 | 合成使用者实际答复 |
| --- | --- | --- |
| 新目录及同轮建议的身份 | synthetic-product-catalog 子目录，非默认 task-id catalog-start-plan；或另给安全子目录 | 采用所建议目录与身份 |
| 四章方案的 plan-acceptance | accept，仅接受本地启动规划；或 revise 并说明修改 | 主智能体实际阅读 payload/plan 后，以 synthetic-user 接受限定方案 |

执行者未重问已给出的范围和档位，未为 doctor、预览、创建、context、阶段推进或补两份辅助骨架追加审批。start 默认生成 14 文件且无辅助卡，后续只按新需求补 environment/progress，未知运行和业务字段保持为空。实际回答前 stage=plan、can_advance=false；回答后 ready/completed_locally 有效，但 business_system_state=not_queried。主智能体另外实际运行 context --check 核对三项检查、身份和索引，而非仅相信子智能体报告。

完整实际读取、命令、问题与答复由执行者记录在隔离测试根，并以[启动原始日志的脱敏副本](records/38-cold-start-record.md)随仓库交付。首轮待答段按历史时点理解，最终状态见其当前阶段与末尾执行结果。临时副本基点为 961ef4b，与联合回归的生产代码/技能/模板一致；本票仅追加测试与说明，不将机器路径、原始工作区或真实业务资料提交到分发仓库。

### 换执行者的故障续接

在同一项目上由测试协调员制造两次真实文件系统冲突，保存原始公开回执后，只移除自己造成且已验证的空目录障碍。另一名 gpt-6-luna/max、fork_turns=none 执行者仅获得项目入口、原始回执和“保留已知方案/决定、按原档位接手”的要求；不读取首个执行者记录、旧聊天、测试协调脚本或私有实现。

实际读取链为项目 AGENTS.md/总览 → 本机框架定位文件及原始回执 → 框架入口和 workflow-router → context/status → 当前事实、验收规则和已有交接材料；补总结时再读取公开帮助、project-start 及 project-documents。初次 context 显示索引不匹配，但实际 ready 事实与三项检查仍通过；不能把旧索引失败解释成方案未完成。

| 独立接手的实际结果 | 主智能体独立核对 |
| --- | --- |
| task-plan 已完成、索引 incomplete | 只执行回执指定的 context --write；不重放 task-plan、decision 或 advance |
| architecture 已创建、summary pending | 确认障碍已排除、summary 不存在；project-docs 先预览，仅补 summary |
| 沿用 assisted、ready 与实际接受决定 | context --check/status 三项检查通过，索引匹配，无待决定；没有新增业务提问 |
| 既有资料保留，新总结仍 draft | 回执保存的原 16 文件 SHA256 全相同；仅新增 workflow-state.json 和 summary.md，task.json 摘要完全不变 |
| 副本只用于运行公开命令 | 框架 Git 工作树干净，业务系统仍 not_queried；不声明真实实现、客户端 hook 或外部调用已验收 |

可复用的公开恢复命令如下。尖括号为已从项目入口取得的同一绝对路径；从该入口定位的框架源码根目录运行，不把这里的演示 ID 当其他项目的默认 ID：

```text
python -m agent_workflow context <同一项目绝对路径> --task-id catalog-start-plan --write
python -m agent_workflow project-docs <同一项目绝对路径> --task-id catalog-start-plan --with-docs summary
python -m agent_workflow project-docs <同一项目绝对路径> --task-id catalog-start-plan --with-docs summary --apply
python -m agent_workflow context <同一项目绝对路径> --task-id catalog-start-plan --check
python -m agent_workflow status <同一项目绝对路径> --task-id catalog-start-plan
```

原始故障回执/操作后文件摘要和独立执行者完整日志亦随仓库交付：[脱敏回执](records/38-recovery-receipts.json)、[脱敏续接日志](records/38-cold-resume-record.md)。主智能体逐份读取原始文件后另行执行上述核对。仅替换本机路径占位，不更改实际参数、问题、答复或结果；回执摘要是原实测前后比对，不承诺跨机器生成文件的摘要相同。它们全是虚构验收资料，不是业务事实或第二份流程状态。真实客户端弹窗尚未测试，本次两个执行者的合成文字交互不冒充真实用户批准。接手不修改终态证据，也不为补文档创建新任务；将来业务实现需依使用者新范围处理，不能把 ready 改报为已实现。

## 文档对齐与交互限制

当前框架入口、生成项目 AGENTS.md/README、project-start 技能及其按需引用、CLI 帮助均指向公开 project-docs，不指引手工复制模板或重跑 start。33/34 号记录保留历史结果并标明旧补模板方式已替代，不把历史说明当现行操作。验收清单的初始 payload 区分空白演示包与实际用户提供名称/目标的项目启动。

hook 源码/子进程测试不等于受信任 Codex 客户端实际触发，后者没有证明时明确未验证；入口＋CLI 仍可独立完成。结构化弹窗可用时附推荐与备选，不可用时可见文字后备；不以选项控件是否出现改变机检，也不为确定性本地步骤逐命令确认。
