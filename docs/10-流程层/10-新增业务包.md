# 新增业务包

业务包把一个场景的语言和流程接到通用协作底座。新增包应满足底座的统一任务、决定、检查、证据和续接契约；不要复制整套框架，也不要把某个场景硬编码成所有任务的共同流程。

## 文件位置与格式

v0.1 自动发现 agent_workflow/packs/{id}/workflow.json 中的业务包，不需要额外注册。起始结构见 templates/business-pack/workflow.json.tmpl。

workflow.json 使用严格 schema；顶层只含 schema_version、id、name、version、description、templates、stages。每个 stage 只含 id、documents、checks。documents 是框架仓库内存在的文档相对路径；templates 是创建工作区时写入的相对文件路径及文本内容。

首版支持三种 check：

| kind | 必需参数 | 用途 |
| --- | --- | --- |
| json-fields | file、fields | 对工作区 JSON 的指定字段做类型、非空、枚举、相等或数值下界检查 |
| file-content | file、contains，可选 sections | 检查文本标记与非空、非 TODO；sections 要求指定二级 Markdown 章节有正文，标题、注释和代码示例不充数，不代替人工内容质量判断 |
| decision | question、recommendation、answers、required_answer | 要求人回答业务选择；只有当前阶段定义的问题可以用 decision 命令回答 |

每种 check 除 id 和 kind 外只允许表中参数。所有 check 的 id 在整个业务包内必须唯一，不可跨阶段复用。字段规则和文字用法可参照两个示例 workflow.json。包的最后一个终态必须没有待执行的 checks。

## 定义前先收集事实

先明确流程边界、任务负责人、可由资料验证的条件、需要人回答的决定、可接受的证据形式，以及哪些操作不在范围内。未经来源确认的业务规则不能写成默认答案。测试用的虚构资料要显式标为示例。

每个包至少需要说明：

1. 唯一且稳定的 workflow 标识和适用范围。
2. 有顺序的任务阶段，以及阶段切换需要的可机检条件。
3. 无法由现有资料推出时要询问的交互决定。
4. 证据入口和空白 payload 模板。
5. 哪些结果只代表协作任务内部进展，哪些外部动作明确未实现。

## 建模规则

- 阶段只描述协作任务，不借用订单、支付、库存等外部系统的“实时状态”含义。
- 将检查结果与人工业务选择分开；缺少事实就标记待补或询问，不生成默认事实。
- 模板仅提供结构，不预填未经确认的业务内容；初始 payload 为空。
- 阶段数及其检查规则由流程自身决定，不要求所有业务包共用状态机。
- 保持包的检查确定、可解释，并可通过公开 CLI 观察结果。
- v0.1 只按数组顺序线性推进阶段；不支持分支、回退或一个工作区追加多个任务。需要不同业务动作时定义对应业务包，并继续复用 core。

## 开发与验收

新增包时按上述目录和 schema 接入，无需注册，不自行发明第二套插件系统。首版没有动态执行插件，也不提供 ERP、支付、退款或真实平台连接。

至少走公开入口验收：doctor 能检查框架，packs 能列出包，new 能在仓库外创建任务，status/context 能按明确 task-id 定位，advance 默认只预览且 --apply 才推进。hook 单独验证只读和显式定位。统一命令见 [验收清单](../30-触发层/30-验收清单.md)。

任务创建时会把完整业务包目录的内容摘要 pack_digest 固定到 task.json，覆盖 workflow.json、SOP 等文件并忽略 Python 字节码缓存。包内任一受摘要文件变化后，旧任务拒绝静默适配。首版没有迁移命令；保留旧版框架和旧工作区资料。要采用新流程版本时，在新项目工作区创建任务，由人复核后重新录入仍适用的事实。

首版提供的 ecommerce-catalog 和 document-delivery 是完全虚构的机制示例。它们不能作为新增真实业务包的规则来源。
