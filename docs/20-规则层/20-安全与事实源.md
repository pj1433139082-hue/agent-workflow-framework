# 安全与事实源

## 工作区边界

框架仓库包含通用代码、规则、模板和虚构测试资料。具体项目及协作任务的工作区必须放在仓库外。不要把业务证据、凭据或真实用户资料提交到框架仓库。

此框架首版不连接真实业务系统。不会执行 ERP、商品上架、支付、退款或其他真实平台操作。v0.1 每个新工作区只有首个任务，阶段线性前进，不支持分支、回退或追加任务。

## 哪些文件保存事实

| 来源 | 用途 | 约束 |
| --- | --- | --- |
| project.json | 项目标识及项目级事实 | 位于仓库外的项目工作区 |
| tasks/{task-id}/task.json | 任务身份、模式、当前任务事实、决定记录和创建时的 pack_digest | 按 task-id 明确定位；绑定创建时业务包内容 |
| tasks/{task-id}/payload.json | 任务业务资料结构 | 模板为空；实际内容须由来源提供 |
| 本地证据 | 支撑事实与检查的文件 | 保存在工作区，不当作生成状态 |
| 每任务 workflow-state.json | 由任务事实和业务包检查派生的导航索引 | 可重建；不手改；不含机器路径或永久远端许可 |

工作区中的事实文件和证据是输入。workflow-state.json 可重新生成，不应反过来覆盖或取代来源事实。索引漂移或无效时，用 context --check 检查，再通过 context --write 重建；重建索引不等于绕过业务检查。

环境要求和选型理由属于任务 plan.md；按需环境文档记录实际检查，并非第二套状态。框架运行时不约束业务语言或版本，工具自检不等于业务验证；具体分工见[项目环境约定](21-项目环境约定.md)。

## 交互和操作范围

交互决定记录的是谁对哪个待定问题给了什么答案，接受的答案绑定回答时全部任务证据的摘要。证据改变后，原接受答案失效；status 会重新检查已经通过的阶段，避免旧阶段的证据被编辑后仍绕过检查。回答只针对当前决定，不等于持续授权。缺少证据时不能用 full-auto 推断业务事实。

档位是智能体协作节奏约定，不是 CLI 权限沙箱。manual-review 约定实质写入前暂停；assisted 在不能由资料推出业务选择时询问；full-auto 只自动处理确定性检查且不推断业务答案。三种档位使用相同机检；任何 --apply 都是调用者明确发起的本地写入，CLI 不会按模式自动增加审批。

status 的 evidence_valid 表示当前和此前阶段的检查是否通过；completed_locally 表示任务已处于终态且证据仍通过。终态也会随证据变化而失效。旧阶段证据改变后，首版不能回退或重答旧阶段决定；终态资料需要修订时，在新工作区重新审查，并保留原任务记录。decision 只接受当前阶段定义的问题。

## 单次读取核验

status、context 与只读 hook 共用单次有生命周期的核验：同一批次读取身份、业务包和任务证据，内容检查与来源摘要复用该批次材料；多条决定复用同一证据摘要，不逐条重扫证据。每条新命令重新读取，不持有跨命令或会话的事实缓存。项目根目录的辅助文档不会因此纳入任务证据集。

返回视图前重新核对受管文件内容摘要、证据与业务包的文件成员、已观察的文件类型及缺失文件。发现变化时丢弃整批材料并有限重核验（最多三批）；仍在变化则返回结构化 materials_changed，不返回混合的通过结论，不写索引或重放业务动作。编辑停止后可重新执行只读 status/context，不必增加人工确认。

这是对可观察变化的检测，不是多文件原子快照或文件系统事务：材料在观察间变化后又恢复、或在最终复核后变化，无法完全排除。行为仍以同批已捕获内容为准；返回摘要不保证材料此后未改。稳定的身份、业务包或数据错误保持原错误表达，不被无条件重试隐藏。

context 使用同一核验结果比较或重建索引，不重复加载任务。纯查询与 hook 不写事实或索引，也不抢写锁；context --write 只生成索引，不迁移任务或补答业务决定。

## 既有任务的写入协议

advance、decision、task-plan 的默认调用仍是只读预览。--apply 与独立 context --write 共用任务目录的 .task-write-lock：先取得锁，再用新批次核验当前材料。先前的预览、锁前读取和已有索引都不是提交依据。竞争调用立即返回 task_busy，不排队或自动重试；持锁写入后的内部索引刷新不再次抢锁。

准入条件各不相同：advance 要求当前及此前阶段的条件通过；decision 只回答当前阶段定义的问题，其他正文检查未通过不妨碍记录有效回答；task-plan 更新档位/下一步不要求阶段检查全部通过。三者均只提交一次自身的合法局部变更，保留其余身份、决定和事实。提交后用明确的新核验批次生成索引摘要，不能沿用旧 task.json 摘要。

这只协调遵守同一锁协议的框架写入；不会锁住用户编辑器或其他程序，也不是多文件事务。单份 JSON 用原子替换；进程中断、观察间改动后恢复、最终复核后的外部改动仍需按事实检查，不能仅凭锁或阶段猜测已永久通过。

## 写入恢复

new 不覆盖已存在的工作区。初始化中断时可能留下刚创建的工作区供检查；先查看其中的 project.json、task.json、模板和本地证据，再用 status/context 核对状态。不要删除未知内容或重复执行创建来“修复”它。

新工作区的独占占位、不覆盖和部分创建保留是独立生命周期，不并入既有任务的事实变更协议。创建后的索引仍可由 context --write 重建。

应用命令的 completion 回执说明本次本地操作，不代表真实业务系统已执行，也不表示所有内容检查已通过：

| 回执 | 含义 | 安全下一步 |
| --- | --- | --- |
| operation=not_completed | 本命令没有提交目标事实/索引；local_record=unchanged 不代表外部程序未改过资料，也不保证没有暂存/锁目录 | 先读 status，检查错误与当前材料 |
| operation=completed、local_record=complete | 请求的本地写入及生成记录完成 | 续接当前阶段，不跨阶段重放 |
| operation=completed、local_record=incomplete、repeat_operation=false | 事实已提交，但生成索引或清理需要处理 | 保留事实；按 recovery 的同一目标 context --write 修复，不重放 advance/decision/task-plan/new |

若带 lock_cleanup=incomplete 或 file_cleanup=incomplete，先按下述规则检查遗留锁或暂存路径；不自动删除未知替换、不递归清理。解锁/暂存清理失败不能将已经提交的事实改报为未提交。context --write 自身完成后若清理失败也保留完成回执，且不改任务事实。repeat_operation=false 表示不自动重放，不是永远禁止在查明事实及错误原因后再次发起合法操作。

进程异常结束且未拿到可靠回执时，结果仍需核对，不猜已经提交或没有提交。索引修复失败只报告本次索引未完成；不能反推此前事实动作未提交。实测故障与恢复见[任务写入与恢复验收](../30-触发层/36-任务写入与恢复验收.md)。

任务写锁 .task-write-lock 可能因 CLI 进程异常结束而遗留。只有 CLI 报任务正忙且确需恢复时才检查，不要把检查锁加入每次正常写入流程。先确认同一任务没有活动中的 CLI 写入进程；再确认该路径位于预期工作区、是安全的空目录而非链接或重解析点、目录内无记录。随后只移除这个空锁目录，不递归删除，不重做上次操作；最后运行 status/context 核对任务事实和派生索引。

框架正常清理只移除其观察到的同一空锁目录。锁身份变更、非空、链接或访问受限时保留路径并提示检查；这不是抵御恶意文件系统替换的原子删除保证。任何 .write- 暂存遗留也只在明确属于本次写入且确认无人使用时单独处理，不能用通配符或递归删除“修复”任务。

## hook 的定位和限制

只读 hook 脚本命令为 python scripts/context_hook.py --event SessionStart 或 --event UserPromptSubmit。它只依赖当前会话的 AGENT_WORKFLOW_WORKSPACE 和 AGENT_WORKFLOW_TASK_ID，必须显式指定两者；变量属于会话环境，不是仓库级任务指针。缺失变量时不猜测任务。hook 不读原始 prompt，stdout 只输出官方 hookSpecificOutput 导航；hook 和 doctor 不写工作区。

hook 输出可用的框架文档绝对路径由运行时提供。配置位于 .codex/hooks.json，通过 git 仓库根目录和 commandWindows 定位脚本。官方配置说明见 [Codex hooks](https://learn.chatgpt.com/docs/hooks)。配置不能证明某一 Codex 客户端已经调用它：客户端版本、信任状态会影响触发。hook 不可用时，按仓库 AGENTS.md，再显式运行 context/status。

## 业务包版本

task.json 中的 pack_digest 固定任务创建时完整业务包目录的内容摘要，包括 workflow.json、SOP 等文件并忽略 Python 字节码缓存。包内内容改变时，旧任务拒绝静默适配。首版没有迁移命令：保留旧版框架和原工作区资料；需要新流程时，在新工作区创建任务，人工复核仍适用的事实后再录入。

## 防止把示例误作事实

ecommerce-catalog 仅表示电商商品资料审核样例，流程 collect → review → ready 的 ready 不等于上架。document-delivery 的 draft → validate → complete 只覆盖本地文档。两个包的模板 payload 初始为空，fake 测试资料只能证明底座能运行，不能证明真实业务流程已验收。
