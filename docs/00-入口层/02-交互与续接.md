# 交互与续接

## 档位控制暂停时机

任务创建时选一次档位，恢复时沿用该设置。档位不改变该任务能接触的数据或系统，也不改变业务包的机检规则。它是智能体协作约定，不是 CLI 权限沙箱；任何 --apply 都是调用者明确发起的本地写入，CLI 不会因档位自动增加审批。

| 档位 | 何时继续 | 不能做的事 |
| --- | --- | --- |
| full-auto | 条件可由现有任务资料确定时继续机检和推进 | 不能把缺失的业务答案猜成已确认 |
| assisted | 确定性步骤自动推进；缺少业务决定时询问并记录 | 不能把回答扩展成永久许可 |
| manual-review | 到实质写入前停下来，等人审核 | 不能绕过审核继续写入 |

同一任务不会因每条命令反复选档，也不逐命令要求审批。所有档位都执行相同机检。真实退款、支付和平台操作没有实现。

## 交互决定

交互决定用于表达现有事实无法推出的选择。context 应显示待回答的决定及其 ID。回答时必须使用该 ID，并提供回答者。以下 PowerShell 示例中的工作区、任务 ID、决定 ID 和回答者均应替换为当前任务的实际值：

    $workspace = Join-Path $env:TEMP 'agent-workflow-demo'
    python -m agent_workflow decision $workspace --task-id catalog-review-001 --decision-id decision-id-from-context --answer accept --by demo-operator --apply

answer 值由该业务包定义；上例中的 accept 不能泛化为任意业务确认。记录后再看 status/context，确认回答归属正确。若来源资料变化导致答案不再适用，应由人重新核对任务事实。

每条接受的决定绑定回答当时全部任务证据的摘要。任何证据变化都会使原接受决定不再满足检查；status 会重检已经通过的阶段，防止编辑旧证据绕过检查。只有当前阶段定义的决定问题能由 decision 回答。若旧阶段的证据在推进后被改动，v0.1 不支持回退或重答旧阶段决定；创建新工作区重新审查，并保留旧任务记录。

## 预览、写入和计划

- status、默认 context、默认 advance、doctor 和 hook 用于查看或预览。
- advance 默认预览；只有显式 --apply 才推进阶段。
- context --write 显式生成状态索引；context --check 检查索引漂移。
- decision 和 task-plan 的 --apply 写入任务记录。
- manual-review 约定智能体在实质写入前暂停，但这是协作节奏，不是 CLI 权限控制；执行者仍须审阅每个 --apply 的本地变更。

task-plan 记录由人提供的下一步文字和档位，不会取代任务事实或交互决定。以下示例的文字由操作者填写：

    python -m agent_workflow task-plan $workspace --task-id catalog-review-001 --next-action '由操作者填写的下一步' --mode assisted --apply

## 按明确身份恢复

续接时使用原项目工作区和 task-id：

    python -m agent_workflow status $workspace --task-id catalog-review-001
    python -m agent_workflow context $workspace --task-id catalog-review-001

不要仅凭当前目录、最近修改时间或机器环境猜任务。任务事实与生成索引不一致时，先按安全与事实源规则检查，再使用 CLI 的检查或生成选项修复索引。

task.json 保存创建时业务包目录的内容摘要 pack_digest，包含 workflow.json、SOP 等文件。若这些内容后来发生变化，旧任务会拒绝静默套用新流程。v0.1 没有迁移命令：保留旧版框架和原工作区资料；要使用新流程版本时，在新工作区创建任务，并明确复核和转录仍适用的事实。

首版只有线性阶段推进。status 返回 evidence_valid 表示当前及之前阶段的检查是否仍通过；completed_locally 表示处于终态且当前证据通过。终态不是永久保证：之后修改证据会使 evidence_valid 变为 false，但任务不会回退，也不能重答旧阶段决定。对此类修订要创建新工作区，并保留原完成记录。

## 只读 hook

hook 脚本支持 SessionStart 和 UserPromptSubmit 事件：

    python scripts/context_hook.py --event SessionStart
    python scripts/context_hook.py --event UserPromptSubmit

hook 从当前会话显式读取 AGENT_WORKFLOW_WORKSPACE 和 AGENT_WORKFLOW_TASK_ID。它不是仓库全局指针，不会选最近任务，也不读原始 prompt 或写任务文件；只向 stdout 输出官方 hookSpecificOutput 格式的只读导航信息。未配置、不可用或客户端未触发时，人工阅读仓库 AGENTS.md，再用 context/status 按 task-id 定位。

配置位于 .codex/hooks.json，使用 git 仓库根目录定位脚本，并提供 commandWindows。客户端须支持该配置且信任当前仓库；配置已交付不代表客户端实际触发。官方说明见 [Codex hooks](https://learn.chatgpt.com/docs/hooks)。验收方法见[验收清单](../30-触发层/30-验收清单.md)。

在终端设置 AGENT_WORKFLOW_WORKSPACE、AGENT_WORKFLOW_TASK_ID 只影响该终端及其启动的子进程，不会修改已经运行的 Codex 桌面会话。若客户端没有继承这两个值，就按 AGENTS.md 和 CLI 显式指定工作区与任务；不要声称客户端已自动定位或已验证触发。
