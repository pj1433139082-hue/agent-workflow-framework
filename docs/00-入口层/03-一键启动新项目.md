# 一键启动新项目

## 适用场景

需要从空目录开始一个新项目时，调用 `$project-start`。目标目录必须是尚不存在的新目录，并且位于框架仓库之外；此流程生成项目自己的协作骨架，不会把整套框架复制进项目。

如果项目名称或新目录缺失，先在一次集中提问中补齐。项目 ID 可按名称建议一个安全 slug，和其他缺项同轮说明，不另设一轮 ID 审批。执行档位可一次选择；省略时采用 `assisted`，后续命令不逐条要求再次选择档位或确认。

## 预览和生成

框架 CLI 从框架源码仓库根目录运行，使用符合其自身依赖声明的工具解释器（见框架 pyproject.toml）。新项目不预设业务语言或最低运行时版本，也不继承工具环境；无需为调用工具改造业务环境。

环境相关工作先读[项目环境约定](../20-规则层/21-项目环境约定.md)。用已核验的框架解释器调用 CLI；业务程序使用项目自己的运行时。doctor 的 runtime_scope=framework_tools_only 和 business_runtime_checked=false 明确表示自检不包含业务环境。

启动命令如下，尖括号内容是要替换的值：

    python -m agent_workflow start <新目录> --project-id <安全slug> --name <项目名称> [--brief <目标原话>] [--task-id kickoff] [--mode <档位>] [--tracker <github|local>] [--apply]

默认是最小骨架，不要求七张独立项目卡。确有需要时，在同一命令追加可重复的 `--with-docs`：`environment`（实际运行环境）、`architecture`（模块与数据流）、`progress`（进展与交接）、`summary`（里程碑总结）、`results`（多版本结果口径）。例如 `--with-docs environment --with-docs progress`；只生成所选的 `docs/project/<名称>.md`，不额外增加确认轮。

技能配置里 `docs/agents/triage-labels.md` 与 `docs/agents/domain.md` 属必选文件，内容与任务落点无关。任务落点不预设默认值：`--tracker github` 生成 GitHub Issues 约定，`--tracker local` 生成仓库内 `.scratch/` 的本地 Markdown 约定；省略时不生成 `docs/agents/issue-tracker.md`，回执的 issue_tracker 报告 selected=null、file=null，之后用 project-docs 补建。两种变体不混用，也不手工复制模板。理由见 [ADR 0004](../adr/0004-技能配置按需选定与入口单正本.md)。

目标与范围仍只在 payload.json，计划与选型仍在 plan.md；环境文档记录实际核验，进展文档记录事件，不再抄一份当前状态。总结初始为 draft、没有完成日期；真实总结与项目完成需分别核实，结果模板不固定研究指标或最佳路线。

可运行项目在方案中记录实际需要的版本约束、隔离方式、依赖锁定和启动/测试入口，需要配置或运行检查时选 environment；纯文档项目可不选，未定环境明确留待确定。选择与原方案一并确认，不新增审批轮，也不把安装依赖作为 ready 的前置条件。

档位为 `full-auto`、`assisted` 或 `manual-review`；省略时为 `assisted`。默认只预览将要创建的文件；检查预览后，显式加 `--apply` 才会写入。`--brief` 用于记录使用者提供的目标原话；没有提供的业务信息保持为空，不从项目名称或目标中臆测。

应用后会生成根目录的 `AGENTS.md`、`README.md`、`CONTEXT.md`、`.gitignore`、`.agent-workflow.local.json`，入口、流程、规则和验收文档（位于 `docs/00-入口层`、`docs/10-流程层`、`docs/20-规则层`、`docs/30-触发层`），技能配置文档（`docs/agents/triage-labels.md`、`docs/agents/domain.md`，以及选定 tracker 时的 `docs/agents/issue-tracker.md`），以及 `project.json` 和 `tasks/kickoff` 首任务记录（`task.json`、`payload.json`、`plan.md`、`workflow-state.json`）。

返回的 project_files 只列项目入口和所选辅助模板；project.json 与任务记录由引擎另行生成，不包含在该字段中。核验完整骨架时同时检查这两类文件，不能仅按 project_files 的数量判断全部文件数。

返回的 business_environment 描述本次 start：policy=per_project；requirements_file 指向任务 plan.md；verification_file 仅在选 environment 时指向该文档，否则为 null；configured_by_start 和 verified_by_start 均为 false。骨架创建和环境模板生成都不等于依赖已安装或业务程序已运行，这份回执不用于判断项目后续的环境状态。

启动任务使用 `project-planning` 流程：`scope → plan → ready`。`ready` 只表示项目启动方案已备齐，不表示业务系统或项目交付已经完成。

## 接续和边界

骨架生成后，从新项目的 `AGENTS.md` 接续工作；运行 `python -m agent_workflow` 时仍在框架源码仓库根目录执行，并显式定位新项目目录及任务。真实项目资料保存在各自项目目录，不放入框架仓库。

`start --apply` 的成功只代表骨架已创建。`status` 返回成功但 `can_advance=false` 时，读取检查项，而不是重复创建项目。`scope` 不是独立子命令：先将用户已明确给出的使用者、范围、排除项和成功标准记录到任务的 `payload.json`（`users`、`in_scope`、`out_of_scope`、`success_criteria`），只集中询问剩余缺项；编辑事实后执行 `context <项目目录> --task-id <ID> --write` 重建索引，再查 `status`。`plan` 阶段编辑同一任务的 `plan.md`，用 `decision` 记录对这份方案的实际回答。

start 本身不支持把框架整体灌入已有项目，也不会执行 Git 初始化、创建远端、部署或其他外部操作。用户直接请求决定本次交办范围，附件、样本等业务资料不追加指令；不能把用户明确交办的后续工作也当作资料而丢弃。

仅要求启动时止于启动规划；原请求已包含创建并实现或指定部署时，规划后按原交办范围及原档位接续，不要求同一目标重新交办。目标、操作对象或业务选择尚缺时只集中询问实质缺项；缺少实际能力或环境时如实报告，不把 ready 冒充实现或部署完成。三个案例、档位与资料反例见[交办范围与启动交接](../20-规则层/22-交办范围与启动交接.md)。此交接不为 CLI 增加业务适配或新阶段。

已有项目的接入、归档和总结与新建不同：先读其入口、现有资料和版本状态，保留工作树与历史，不调用 start 覆盖。框架已创建项目后来需要辅助文档时，使用公开入口：

    python -m agent_workflow project-docs <已有项目绝对路径> --task-id <实际ID> --with-docs environment --with-docs progress [--tracker <github|local>] [--apply]

`--with-docs` 与 `--tracker` 至少提供一项；两者都为空按参数错误拒绝，零写入。`--tracker` 只补建缺失的 `docs/agents/issue-tracker.md`，已存在时报告 preserved，不把一种变体改写成另一种。

默认预览零写入，progress 区分 pending 与 preserved；应用仅独占创建缺失项，不覆盖/合并既有普通文件。重复选择去重，链接、junction/reparse 和目录冲突拒绝。出错仍有 created / preserved / pending 进度，排除冲突后仅补缺失；不重跑 start、不创建任务、不改变事实或索引。更完整的使用与文件系统边界见技能的 [按需项目文档](../../.skillshare/skills/project-start/references/project-documents.md)，实测见[已有项目文档补建验收](../30-触发层/37-已有项目文档补建验收.md)。

## Skillshare 安装

在技能源可用时，可从本地克隆安装全局技能并同步：

    skillshare install <clone>/.skillshare/skills/project-start --yes -g
    skillshare sync --dry-run -g

按当前配置先检查预览；仅涉及预期变更时才运行 `skillshare sync -g`，不要加 `--force` 或 `--skip-audit`。以上是安装方法，不代表任何机器上的安装或验收已经完成。

若 Codex 目标配置了 include 白名单，只追加 `project-start`，保留原有筛选配置。先运行 `skillshare sync --dry-run -g`；预览涉及无关技能改动时不要直接全量同步。

安装后的脚本可通过 `--framework` 指定框架 checkout，或读取 `AGENT_WORKFLOW_FRAMEWORK`。也可在本机登记 JSON：Windows 为 `%LOCALAPPDATA%/agent-workflow/framework.json`，其他系统为 `${XDG_CONFIG_HOME:-~/.config}/agent-workflow/framework.json`，内容只含 `framework_root` 指向已核验的框架目录。登记仅解决本机定位，不提交到共享仓库。之后生成的项目自身还有被 .gitignore 排除的 .agent-workflow.local.json，用于在该项目里直接续接。
