# 05-智能体提问纪律与问答分流

本指南是通用智能体在协作过程中的**交互与提问纪律**，旨在彻底解决智能体“喋喋不休、碎步打扰、重复求证、问已知事实”的负面体验。智能体必须在发问前完成事实查证，只将不可推导的业务决定交由使用者确认。

---

## 一、 智能体提问六大铁律

1. **可算不问（Evidence-First）**：
   - 凡是能从项目代码、测试结果、Git 历史、配置文件（如 `package.json`、`pyproject.toml`）或环境证据中自行推导或计算的事实，**严禁向用户提问求证**；
   - 智能体必须先查明事实，再进入下一阶段。
2. **批量集中（Batch Questioning）**：
   - 当前任务阶段若存在多个待确认的业务决定，必须合并为**单轮集中提问**；
   - 每个问题必须带编号（Q1, Q2, ...），并清晰列出**背景、业务影响、推荐选项与备选选项**；
   - 严禁每个回合问一个碎步问题、分多轮拉扯。
3. **一键确认（Single-Stroke Approval）**：
   - 必须支持使用者回复“全部按推荐”、“按默认”或数字编号一次性通过整轮问题；
   - 收到“全部按推荐”后，智能体必须在本地状态机中将各项具体推荐值分别持久化写入（通过 `decision` 命令），禁止直接记录无业务语义的“按推荐”三个字。
4. **可见消息保底（Visible Text Fallback）**：
   - 所有问题与选项必须**首先在可见对话文本中完整输出**，然后再尝试调用客户端结构化选择组件（如 ask_user_question 等）；
   - 严禁只回复“请看弹窗”，确保在客户端控件未渲染或不支持交互时交互依然顺畅。
5. **问过即锁（Evidence-Locked Decisions）**：
   - 使用者确认决策后，智能体立即通过 `python -m agent_workflow decision` 写入任务记录，并自动绑定当时文件内容的 SHA256 证据指纹；
   - 在证据未发生变更前，后续步骤推进与断点恢复**绝不重复询问同一问题**。
6. **只读零打扰（Zero Disturbance for Queries）**：
   - 纯代码阅读、文件定位、状态查询、诊断检查或进度汇报任务，**严禁弹出档位选择或业务审批**，直接执行并汇报结果。

## 二、 场景分流提问矩阵

| 协作需求类型 | 智能体自动查或做 | 真正需要提问的情形 | 本轮绝不发问的事项 |
| :--- | :--- | :--- | :--- |
| **只读查看 / 诊断 / 检索** | 自行读取代码、状态、检查日志并汇总事实 | 目标完全无法定位或路径不存在时，问一次定位信息 | 选档、命令执行授权、可算出的代码事实 |
| **全新项目启动 (`start`)** | 自动生成安全 slug、初始化轻量骨架并检查工具环境 | 项目核心目标留空、缺少关键受众或排除项时 | Python/Node 版本、模板文件位置、是否允许写入 |
| **老项目纳管与改造 (`adopt`)** | 自动扫描已有源码、Git 历史、依赖文件并生成环境草稿 | 老项目已有重名冲突需裁决、或改造边界不明确时 | 重新询问老项目已有技术栈、是否允许创建 docs/ |
| **方案设计与技术选型** | 自动提取既有架构模式并给出针对性的推荐选型方案 | 存在不可逆的重大架构取舍，且两方案各有优劣时 | 询问语言版本、基础库等已锁定的环境事实 |
| **编码实现与测试推进** | 自动根据方案编码、运行单元测试并修复非实质报错 | 遇到原方案中未覆盖的破坏性改动或测试断言冲突 | 每条执行命令的执行许可、已测通的代码片段 |
| **外部部署与生产发布** | 自动核对发布产物签名、完整度与配置门禁 | 用户未提供明确的发布目标或凭据缺失时 | 伪装成部署完成、把本地规划完成误报为线上发布 |

## 三、 单轮集中提问的标准模板

当智能体识别出当前阶段存在阻塞的业务决定时，必须按以下标准结构输出：

```markdown
依据当前任务事实，我们需要确认以下 N 个业务决定：

---
### ❓ Q1 - [决定标题]
* **背景与现状**：...
* **备选方案**：
  * **选项 A（推荐）**：...
  * **选项 B**：...
➡️ **推荐**：选项 A，原因在于...

---
### ❓ Q2 - [决定标题]
...

您可以直接回复：“全部按推荐”，或指定具体编号选项（如 “Q1 选 A，Q2 选 B”）。
```

收到回复后，智能体执行：
```powershell
python -m agent_workflow decision <工作区> --task-id <任务ID> --decision-id <决定ID> --answer <具体答案> --by <操作者> --apply
```
随后自动重查 `status` 并继续推进，不就同一方案追加任何形式主义的二次确认。
