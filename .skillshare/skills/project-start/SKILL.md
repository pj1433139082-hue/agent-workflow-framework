# 新项目启动

把用户的项目想法转成独立工作区；框架和技能留在各自维护源，不复制整套框架、真实旧项目或模型资料。使用本技能的 `scripts/start_project.py` 定位框架并调用公开 CLI，不手工拼另一套状态机。

## 定位与一次提问

先读取当前工作区已有 AGENTS.md，保留使用者的工具、代理和操作边界。执行 `python <本技能目录>/scripts/start_project.py --locate`；脚本读取显式框架目录、AGENT_WORKFLOW_FRAMEWORK、当前项目本机定位、本技能的源码 checkout 或本机框架登记。无法唯一定位时只问一次框架目录，不猜某个固定盘符，不自动下载。

助手失败先按结构化错误类别处理，见 [启动助手诊断](references/start-diagnostics.md)。工具版本或助手参数错误不重复询问框架位置；已转发 CLI 的实际结果与部分完成回执不得改写或自动重放。

集中核对项目名称、新目录和一句目标。用户已经给出的不再问；目标允许先留空进入澄清。未给项目 ID 时建议一个安全英文 slug；目录必须在框架外且尚不存在。已有目录只报告并建议新位置，不把“开新项目”理解为覆盖旧项目。当前项目尚无入口时不要要求它先有 AGENTS.md。

默认轻量启动，不要求七张项目卡。需要运行环境、架构、长期进展、总结或结果口径时，读 [references/project-documents.md](references/project-documents.md)，按真实需要选择辅助模板，和其他缺项同轮说明。为框架已有项目补文档走该引用中的 project-docs；历史项目接入/归档仍先只读盘点，不调用 start 覆盖。

档位只选一次：assisted（推荐）连续处理已交办本地工作，只集中询问新增业务决定；full-auto 不猜业务答案；manual-review 在实质写入前停下。用户已选档或采用已展示推荐就沿用；不把 --apply 变成每条命令都问一次。

## 创建和接管

先阅读定位到的框架 AGENTS.md 和 `docs/00-入口层/03-一键启动新项目.md`。不为新项目预设语言或最低运行时版本；框架 CLI 的兼容声明只属于工具自身，按框架的依赖声明核对，不写成业务项目的环境要求。

创建可运行项目或处理环境需求时，读框架 `docs/20-规则层/21-项目环境约定.md`。业务运行时按当前需求独立选择：要求、隔离、锁定和启动/测试入口记在任务 plan.md，实际核验按需放 environment.md；需要配置或运行检查时选择 `--with-docs environment`。纯文档项目不强制安装运行时或生成环境文档；未知项留待确定，相关业务选择并入原方案确认，不逐个依赖追加提问。

调用定位/转发脚本使用已核验的框架 Python；不要把当前激活的业务解释器默认当成兼容工具。创建骨架不包含依赖安装或运行验证；只有后续已交办实际实现/环境配置时，才检查已有配置、按项目要求配置隔离环境和执行相关命令，不更改系统默认解释器、PATH、代理或 VPN。

通过本技能脚本转发命令（每个参数独立传递，不拼接 shell；框架路径可用 `--framework` 显式指定）：

```text
python <本技能目录>/scripts/start_project.py --framework <框架目录> -- start <新目录> --project-id <ID> --name <名称> --brief <用户原始目标> --mode assisted
```

检查默认预览的目录和文件清单。明确交办创建且范围齐全时，同一命令加 --apply 即可执行；manual-review 则先按所选节奏暂停。调用仅创建本地项目骨架，不初始化 Git、不建远端、不上传或部署。doctor 只检查框架工具；start 的 business_environment 回执明确本次未配置、未验证业务环境，不能把模板或规划 ready 当作可运行证明。

随后用同一脚本调用 `status <项目绝对路径> --task-id kickoff` 与 `context`，读新项目自己的 AGENTS.md。如果用了自定义 task-id，所有后续命令都使用该 ID。先把用户已明确给出的使用者、范围、排除项和成功标准记入 payload.json；只集中询问仍缺少的业务信息，不为关闭检查项重复问已回答的问题，也不能把示例或空模板当业务事实。编辑事实后用 context --write 重建索引，再查 status。

默认规划流程 scope → plan → ready。把项目启动方案、风险和验收口径合成一个 plan-acceptance 问题，展示 accept / revise；用户实际回答后才使用 decision。ready 只表示本地启动方案有效，不代表整个业务系统完工。后续开发需求另行安排，不自动把规划的三阶段当成所有业务动作的流程。

## 续接和结束

后续在新项目里从 AGENTS.md 和当前任务 context/status 接管，恢复 task.json 中的档位；每个任务的 workflow-state.json 是生成索引，不手改它或从聊天猜阶段。框架移动后修正本机定位，不重建或覆盖业务事实。

已有项目后来需要辅助文档时，沿用已定位的工作区、真实 task-id 和档位，按上述引用调用公开 project-docs 预览/补建；不手工复制模板、不重跑 start、不另建任务。选择与其他实质缺项同轮说明，不逐张问确认。该命令不改变任务事实或索引；部分失败按 progress 只补缺失，与事实已提交后的索引修复分开处理。

创建若返回事实已完成但索引不完整，只执行返回的 context 修复，不重复 start。结束时给出项目目录、入口、实际阶段、已验证/未验证和下一步。外部操作只在用户另行交办具体目标时处理；本技能不把自动档位或方案接受写成永久许可。
